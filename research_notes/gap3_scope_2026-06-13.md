## 3. The core GAP-3 deliverable

The GATE-2 architecture does **not** need a single all-q genuine measure-preserving map T on T^q with an invariant probability measure μ to be built from scratch. The architecture already bypasses this through the confinement engine. Specifically:

**What `full_bound` / `essSup_ge_of_no_sustained_strict` requires:**
1. A `T : ℝ×ℝ → ℝ×ℝ` (any self-map)
2. A `μ : Measure (ℝ×ℝ)` with `IsProbabilityMeasure μ`
3. `MeasurePreserving T μ μ`
4. `μ (Taha l)ᶜ = 0`
5. `∀ᵐ x ∂μ, Pgen l x ≤ M`
6. The (C′) condition: `∀ orbit, (∀ n, orbit n ∈ Taha l) → (∀ n, orbit n+1 = T (orbit n)) → ¬(∀ n, Pgen (orbit n) < 1/l³)`

**What is currently used for items 1-5:**  
`perq_essSup_ge_q17..21` uses `Tmap l` (the SCALAR branch only) as T, with a `Tmap`-invariant probability measure on `Dcorr`. This gives the scalar-orbit lower bound. The invariant measure for the scalar `Tmap` is the BCZ 2dxdy measure, but in the current Lean statements it appears only as a hypothesis `hinv : MeasurePreserving (Tmap l) μ μ` — the existence of such μ is not constructed in Lean, it is assumed. This is acceptable for the conditional theorem.

**What GAP-3 needs for the GENERAL (multi-branch) orbit:**  
The key obstacle is item (6) — the (C′) condition for a GENERAL genuine orbit (not just a scalar one). This is exactly what `BCZHeckeConfinement_VERIFIED.lean`'s `genuine_no_sustained_cusp_discharged` discharges, conditional on:
- `htri` — the branch trichotomy for each orbit step.

So the CORE GAP-3 deliverable is:
```

    (orbit n ∈ Dcorr l ∧ orbit (n+1) = Tmap l (orbit n)) ∨  -- scalar step
```

for orbits of the genuine all-q Hecke-BCZ map. The `hbridge` (`g_corr ≤ g_true`) connective is handled separately in the L1 skeleton, and is an assumption (`hbridge` parameter) in `no_sustained_corridor`.

**How `htri` and `hbridge` relate to `(a)` and `(b)` of the task:**  
- `htri` is the trichotomy — it makes `genuine_no_sustained_cusp_discharged` unconditional. Once `htri` is given, (C′) holds.

## 5. STUB (A) and STUB (B) assessment: engineering vs. genuine-new-math

### STUB (A): torsion classification

The algebraic half IS PROVEN: `torsion_quantization` in the WIP file shows that for digits k ∈ {1,2,3}, `tr(F k) = chebCos l j` for an explicit j, which equals `2cos(jπ/q)` geometrically (`torsion_quantization_cos`). This covers the single-corridor elliptic traces.

What STUB (A) actually requires that is NOT proven:
1. **Branch space exhaustiveness**: every step of a genuine Hecke-BCZ orbit at q=18 (or any q) is on one of the branches indexed by i ∈ {1, ..., q-1}. This is a property of the genuine map definition.
2. **The {F-family, deep-mid} partition of branches**: that branches i ∈ {2,...,q-2} (the non-scalar branches) are either in the "deep-mid ejection box" or the "cusp branch" regime.

This is **genuine new combinatorics**, NOT the KAM obstacle. The KAM/discreteness obstacle from `goal1.5_uniform_obstruction` (FINDING 3) was about the CLUSTER SIZE growing with q — here we need something different: that the branch partition is exhaustive for the confinement argument. This requires the genuine piecewise map to be defined in Lean.

Assessment: **Hard** but not open mathematics. It requires formalizing the genuine branch decomposition (already partially done in the WIP's `genStep` / `branchIdx` machinery). The `IsFstep`/`IsDeepMid` predicates in the skeleton are currently just `True` — they need to be connected to the real branch indices via `branchIdx`.

### STUB (B): long-run ⟹ scalar bookkeeping

This is **engineering** in the following precise sense:
- `Eject` (proven) says: a deep-mid sub-threshold step forces the NEXT step ≥ 1/λ³.
- `Switch` (proven) says: a W_q switch forces |trace| ≥ 2 (non-elliptic), so the corridor collapses.
- The bookkeeping needed is: track which of the 6 observable `P c(i+k) < 1/λ³` values correspond to scalar products, and show the conclusion follows by case analysis on branch types at each of the 6 steps.

The `BCZHeckeConfinement_VERIFIED.lean` file has already done this at the sequence level for the abstract `(scalar, deepmid, cusp)` trichotomy (`subthreshold_forces_scalar`). STUB (B) is essentially a special case of that theorem specialized to the 6-window form. The main work is the "product identity" step: showing that `P c(i+k) = c(i+k) · c(i+k+1)` when the step is scalar, which requires the branch selector to tell us the step IS scalar.

Assessment: **Routine** once STUB (A)'s branch classification is in place. Given `IsFstep` defined concretely and the `Eject+Switch` hypotheses, the 6-window bookkeeping is a finite case split handled by `nlinarith`/`omega`-style tactics.
